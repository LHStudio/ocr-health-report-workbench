# 统一计算链与报告门槛（2026-10-21 用户确认版）

本文件与 config/standards_review.json 是当前计算口径。10-18 标准导出及此前版本为历史记录，不叠加为第二套标准。

## 1. 需求与能量的唯一来源
- 蛋白质、碳水沿用已确认的体重×项目系数及训练期适用范围；不根据实际吃了多少改变需求，不新加营养容差。
- 有有效 BMR 上下限且有可用活动消耗时，采用 BMR＋日均活动净消耗。现有足球、篮球课表与个人训练覆盖值仍沿用，力量课时从已包含的总课时中扣除，避免重复计算。
- 否则使用既有 EER；不把裸 BMR 当全天需求，也不在已含活动的 EER 上再次加运动消耗。明确填写零训练分钟与缺少活动估算不同；有效零活动可以与 BMR 合计。
- EER 所需性别、年龄、活动级别缺失，或现有表不支持该人时，保留缺失并暂停配餐，不猜数。BMR 部分填写、非有限、非正数或倒置仍报错，不掩盖无效输入。
- 参考区间采用原上下限；EER 实际能量评价沿用 90%–110% 接受带。该接受带不是新的脂肪目标能量。

## 2. 脂肪：目标能量反推克数，只影响总评
- 目标能量为 E 时，脂肪参考范围是 [E×20%÷9，E×30%÷9] g/天。
- 目标能量为 [Emin,Emax] 时，采用 [Emin×20%÷9，Emax×30%÷9] g/天；不取擅自设定的中点。
- 实际脂肪克数仅与这个范围比较，评价只写“适中 / 不足 / 过多”。不再按实际三大营养素供能占比给第二个等级。
- 三大营养素供能图只是实际摄入构成，不是脂肪等级标准。
- 脂肪不改写谷类、豆类、薯类、肉类等小类的规则、评价和分配量。不因脂肪不足添加烹调油、零食或未记录食物。
- 联合试算按能量、蛋白质、碳水及分项规则求可行量，不以脂肪为小类分配约束。汇总后单独复验脂肪目标；失败仅形成整体未通过状态，不倒推更改小类。不得用试算失败认定所有可能食谱均无解。

## 3. 各项规则始终独立
谷类≤谷豆薯能量合计80%、豆类≥5%、薯类≥15%；畜禽肉≤肉类重量70%、水产品≥30%；肉蛋奶蛋白/总蛋白≥50%。
以上是不等式，不强迫等于端点；一组求解克数不是规范上下限，不能覆盖原比例规则。
奶类、蛋类、蔬菜、水果、坚果沿用原数量规则。只有下限的规则不据此判定过量。
评价栏仅输出“适中 / 不足 / 过多”，数据不完整保留“-”；不改为“能量占比偏高”等字样。比例标准保留原单位，以便复核。
原始记录只有“零食”时，按用户指定的薯条API密度估算，留下代理换算记录；明确“糕点”等命名食物保留原映射，不重写为薯条。计入实际能量、蛋白质、碳水、脂肪和钙合计一次。API缺少薯条或其成分无效时不伪造数值、也不回退为蛋糕。
零食是固定定性规则：**不建议吃零食**。不因能量缺口、脂肪缺口、是否吃过或配餐未通过而改变。
谷类、豆类、薯类分别展示；畜禽肉、水产品分别展示，不加肉类总项。

## 4. API与反推
使用原有 API 食物密度（客户端既有每100g口径）反推，保留数据来源；豆腐、苹果汁由用户自行核对，本次不改、不替换、不以固定指纹设置阻断。
仍阻断缺失参数、非有限值、负值及全零占位。薯条出现正能量但三大营养素全零时单独待核对，不把这项新增判断泛化为其他类别的成分认证。数值筛查不代表成分已认证；4/4/9与API能量差异不自动判为API错误。
只使用既有十种默认食物，不额外添加油、零食或补充剂。所有食物的营养贡献只计一次，米饭仅承担扣除其他食物碳水后的余量。
求解仅寻找可行组合，不新增“总食物重量最小”营养标准。输出按0.01g精度复算；1e-6仅为计算浮点误差，不是膳食容差。

## 5. 相容性与汇总复验
先计算宏量能量必要包络 [4Pmin+4Cmin+9Fmin，4Pmax+4Cmax+9Fmax] 与能量接受区间是否相交。
这是必要预筛查，不是完整食谱存在的证明；蛋白1.7g/kg仅是既有优选点，不替代蛋白范围。
分项食物用API能量和密度计算，最后汇总复验API能量、蛋白、碳水、脂肪克数、钙及各项规则。API能量不被4/4/9重写，脂肪不再同时对API能量和宏量供能比施加第二套限制。

## 6. 输出门槛
全部数值和数据一致性检查通过，才输出17个独立建议；否则 report_status=needs_review、recommendation_status=blocked，建议数组为空，但保留实际摄入、小类评价、固定零食规则和具体原因。
人工原始记录、结论与明确留空保留。未通过门槛时，人工建议/解读只保存为 withheld 审计字段，不通过手动编辑绕过导出门槛。零食的原人工文字如不同则留作记录，不替换固定规则。
数值通过也不等于唯一或已专业审定的现实食谱；没有给定餐次、可接受份量上限，不擅自编造。

## 尚未确认且不代选的事项
体操被历史导出脚本归为 strength，不能据此认定是用户已确认的项目系数。保留这一待确认标记；其能量仍严格按上述BMR＋活动/EER规则计算，不再重复询问已确认能量、脂肪或API事项。
